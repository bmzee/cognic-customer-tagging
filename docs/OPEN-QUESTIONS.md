# Open questions

Questions this build could not settle by itself. For each one: the choice made for now, why, and who can settle it. The conservative choice wins every time: read-only, explainable, private, smaller.

| ID | Question | Choice for now | Why | Settled by |
| --- | --- | --- | --- | --- |
| Q1 | Should CI run the safety-file schema test against the draft schema? | No. CI skips that one test; it runs locally with `COGNIC_SAFETY_SCHEMA` pointing at a local copy. | The schema is private. Fetching it in a public repository's CI would need a stored read token and would put private content on public runners, where logs and test messages are visible to everyone. | The maintainer: publish the schema, or run this one test in a private CI. |
| Q2 | There is no "personal" data class in the draft vocabulary. Which class marks personal data? | `sensitive`, together with `confidential`. | It is the strictest class that fits customer-level behavioural data. | Cognic's hosting (data-class vocabulary). |
| Q3 | Does running the engine's scripts in the workbench count as a `private` effect? | Settled by design from phase 7: no skill runs scripts any more. Skills and commands are instructions that use the reader's read-only tools (profile "standard"). | The question only returns if a bank wants the print-only engine in a workbench. | Cognic's hosting, only if that is wanted. |
| Q4 | Is a required skill named by its bare ID (`customer-tagging`) or qualified (`customer-tagging:customer-tagging`)? | Qualified. | The hosting design qualifies catalogue names as `<plugin-id>:<skill-id>`. | Cognic's hosting (skill ID resolution). |
| Q5 | Which roles may use the plugin? | `["employee"]` everywhere. | A broad role that a bank narrows through its own role bindings. The name must match an actual admin role binding. | The bank's administrator, at activation. |
| Q6 | `ubuntu-latest` will move to Ubuntu 26.04, which has no Python 3.9 build for `actions/setup-python`. | Keep `ubuntu-latest` and Python 3.9 to 3.13 for now. | The task asked for `ubuntu-latest`; 3.9 is the oldest version the plugin supports. | The maintainer: pin `ubuntu-24.04` or raise the minimum Python version when the move happens. |
| Q7 | Should CI add a second, independent check of the safety file with a pinned JSON Schema package? | Not yet. | It needs the private schema too (Q1). CI stays dependency-free until then. | Follows Q1. |
| Q8 | How is the builder run inside Cognic: on a schedule, and later continuously? | A command-line builder (`python3 -m engine.build`) with two modes: `--rebuild` for scheduled runs first, then `--follow` for continuous updates. Cognic's planned watchers and standing goals would trigger it. | Scheduled rebuilds need nothing new from the host; continuous updates need a long-running or regularly woken process that only the host can provide. | Cognic's hosting (watchers and standing goals). |
| Q9 | How is the bank's read-only data copy mounted, and in what shape? | Two CSV files following the data contract in the README, mounted read-only; the change feed arrives as a JSONL file or a SQLite outbox table. Column mapping from the bank's tables is reviewed configuration. | The narrowest interface that a bank-side export or CDC bridge can produce without giving the plugin a database login. | Cognic's hosting and the bank's data team. |
| Q10 | Where does the plugin's durable store live, writable by the builder and read-only for the reader? | One SQLite file at a path given to both processes; the reader opens it with `mode=ro`. | The store must survive restarts and be shared by two processes with different effects. Hosting has no plugin-owned durable volume yet. | Cognic's hosting (private, durable plugin storage). |
| Q11 | What tier and effect does the builder declare? | Effect `private` (it writes only its own store), tier `worker`. Not declared in `cognic.plugin.json` until hosting says how such a process is admitted. | The safety file must not claim a component the host cannot run yet. | Cognic's hosting. |
| Q12 | Is month-end resolution enough for tag history? | History is recorded at month-end checkpoints; the current state is exact to the day; a tag that started after the last month end shows as "new this month". | A batch rebuild must reproduce history exactly, and evaluating every customer on every day does not scale. Most rules use monthly windows. | The bank's compliance team (audit needs). |
| Q13 | How late can feed events arrive? | `allowed_lateness_days` defaults to 3. An event dated in a month that ended more than that many days before the as-of date is late: it is kept in `late_events`, counted and flagged, and only a deliberate rebuild folds it in. | Bounded lateness keeps history exact and recomputation cheap; the value depends on the bank's feed. | The bank's data team. |
| Q14 | Which sources may the research cite? | Papers, standards bodies, regulators, open-source projects and non-bank vendors. No source published by a bank. | Citing a bank's engineering blog would put a bank's name in this public repository. | The maintainer. |
| Q15 | The regulation research names EU, US and UK frameworks. Do they apply? | They are cited as general principles only. What applies is decided by the bank's regulator and data-protection law. | This repository never names the bank's jurisdiction. | The bank's compliance team. |
| Q16 | How are people's names pseudonymised in a real deployment? | A stable SHA-256 token of the cleaned name with a fixed prefix. | Enough for synthetic data. A real deployment needs a secret key per bank (a keyed hash), or a token the bank's feed already supplies, so tokens cannot be reversed by guessing names. | The bank's data-protection officer and Cognic's credential handling. |
| Q17 | What happens to transactions with no category and no merchant code? | They are "uncategorized"; category-based tags simply do not see them. ISO 20022 bank transaction codes as a fallback, and a cap on the uncategorized share before category tags may fire, are deferred. | The synthetic data has no bank transaction codes; adding a fallback without real codes would be guesswork. | The bank's data team (which codes its feed carries). |
| Q18 | Is the balance after each transaction available, and in which currency? | Optional `balance_after` in the home currency; balance tags are "not evaluated" without it. | Many feeds carry a running balance, but not all. | The bank's data team. |
| Q19 | How many months of tag history should a rebuild reproduce? | `lifecycle_months` = 6 month-end checkpoints; `history_months` = 13 months of transactions. | Each checkpoint costs one evaluation per customer in a rebuild; longer audit history lives in store exports. | The bank's compliance team (audit needs). |
| Q20 | Who owns the taxonomy, and when is it reviewed? | Placeholder owner "the bank's taxonomy owner", review date 2027-04-30, on every tag card. | Ownership is a bank governance decision. | The bank's model-governance function. |
| Q21 | Is the profile store encrypted at rest? | Not by the plugin: the store is a plain SQLite file. | The standard library has no encrypted SQLite, and key handling belongs to the host. The store holds sensitive behavioural data, so the host's volume must be encrypted. | Cognic's hosting (private storage) and the bank's security team. |
| Q22 | How do the builder and the reader share the store safely? | A rebuild writes a temporary file and renames it into place; readers open read-only. The follower writes in place in WAL mode, one transaction per batch, and switches the file back to rollback-journal mode when it exits. A reader that opens the store while the follower runs needs its folder to allow SQLite's shared-memory file (`-shm`); after the follower exits, a plain read-only mount works. | Readers never see a half-built store and never block the builder; a read-only mount alone cannot read a WAL file that is being written. | Cognic's hosting (one writable mount for the builder; for the reader, read-only, plus the shared-memory file if they run at the same time). |
| Q23 | How long are store exports and old stores kept for audit? | Not decided by the plugin; `runs` records each build, and an export is reproducible from the same inputs. | Retention of audit copies is a bank policy. | The bank's compliance team. |
| Q24 | Where do the event versions come from? | The feed must give every change a version that increases per transaction and per customer (a CDC log position or an outbox id). Postings from a CSV copy have version 0. | The winner of each register is decided by version first; a source without versions can only rely on "reversal beats posting, then first event id". | The bank's data team (CDC configuration). |
| Q25 | Who sends the daily clock tick? | Ticks are events like any other: the bank's bridge appends one at the end of each business day. | Time-based tags must change with no new transaction, and the as-of date must never come from the plugin's clock, so runs stay reproducible. | Cognic's hosting (watchers and standing goals) or the bank's bridge. |
| Q26 | Can two customers share a transaction id? | A transaction is identified by customer and transaction id; the same id under two customers is two transactions. | The register key needs the customer, and a feed's ids are usually per account. Stage 1's CSV rule treated the id as global. | The bank's data team. |
| Q27 | How long may a tick take, and how should the feed be batched? | A tick re-evaluates every customer: 17.5 s for 20,000 customers locally, 447.3 s for 200,000 in CI. Events are applied in batches; at 200,000 customers one event per batch costs 110 ms at the median, and batches of 500 reach 340 events per second. | Day windows and tenure change for everyone when the date moves. If this is too slow, a tick can re-evaluate only customers whose rules use day windows or tenure, and month-window customers at month ends. Each batch also counts whole tables for its runs row, which grows with the store; keeping running totals would make single events cheap. | Cognic's hosting (how long a scheduled run may take, and the feed's batch size). |
| Q28 | Which name does `find_customers_by_tag` show? | `display_name` is a label for the record ("Customer C0042"); the store keeps no names. | Names are a proxy for gender and ethnicity and are never loaded. If staff need a name, Cognic can join it from the bank's CRM under its own access controls, outside the plugin. | Cognic's hosting and the bank. |
| Q29 | Where is the store mounted for the reader? | The reader runs as `/app/profile-reader --store /data/profile.db`. The image carries a synthetic fixture store at that path (phase 6); production mounts the real store there read-only, replacing the fixture. | One command and argument list for every environment, as the safety file pins them. | Cognic's hosting (Q10). |
| Q30 | Which MCP protocol versions does Cognic's client speak? | The reader serves both the stateless 2026-07-28 requests and legacy clients that open with `initialize` (2025-11-25, 2025-06-18, 2025-03-26). | Cognic's hosting design plans a standard initialisation profile for its existing client; newer clients are stateless. | Cognic's hosting. |
| Q31 | Where is the reader's image published, and under which name? | The safety file pins `registry.invalid/customer-tagging-profiles@sha256:<digest>`: the digest of the image CI builds reproducibly from this commit, under a clearly invalid registry name. Nothing is pushed anywhere. | Publishing an image is an operator action on Cognic's infrastructure; a reproducible digest lets the operator verify that what they publish is exactly what this repository builds. | Cognic's hosting operators. |
| Q32 | Will the base image digest be refreshed for security fixes? | Pinned to the `python:3.12-slim` index of 2026-10-09. A refresh changes the image digest, so it is a reviewed change with a new pin. | Pinning by digest is what admission requires; updates must be deliberate. | The maintainer and Cognic's hosting. |
| Q33 | How are tools named in an agent file and in the safety file? | The agent file lists the tools as the plugin format names a plugin's MCP tools (`mcp__plugin_customer-tagging_profiles__<tool>`); the safety file's agent, skill and command entries list the bare tool names it declares (`get_customer_tags`). | The hosting design asks for a reviewed exact mapping from source tool names to its own grants (`plugin:<instance>/<tool>`); both forms are finite and exact, and a test keeps them equal. | Cognic's hosting (agent compilation). |
| Q34 | Who is the agent's caller? | The plugin's scope lists the assistant and `customer-profiler`; the agent's own scope lists only itself, so it cannot be granted to other agents by this file. | Agents are bound by an administrator; the safety file only sets the ceiling. | The bank's administrator. |
